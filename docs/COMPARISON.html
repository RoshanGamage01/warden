PM2 vs Warden — Side-by-Side Comparison

Warden is a self-hosted process manager built as a PM2-equivalent for Node 18+. This document compares the two tools feature-by-feature so you can decide which fits your stack — or migrate from PM2 with minimal friction.

At a glance

PM2 Warden
Purpose Production process manager for Node.js and beyond Self-hosted PM2 alternative with built-in telemetry
Language JavaScript TypeScript
License AGPL-3.0 MIT
Node requirement Node 12+ Node 18+
Install npm install -g pm2 npm install -g @roshan-gamage/warden
CLI binary pm2 warden
Daemon IPC Unix socket / TCP Unix domain socket (named pipe on Windows)
Config home ~/.pm2/ ~/.warden/
HTTP API Optional (via PM2 Plus / custom) Built-in on 127.0.0.1:9615
Prometheus Via third-party modules Native /metrics endpoint
Metrics storage External (PM2 Plus cloud) Local SQLite (24-hour rolling window)
Cloud dashboard PM2 Plus (paid) None — self-hosted only

Ecosystem config compatibility

Warden reads the same ecosystem file formats PM2 uses (ecosystem.config.js, ecosystem.config.json, and other *.config.js files). Field names follow PM2 conventions:

// Works with both PM2 and Warden
module.exports = {
  apps: [
    {
      name: 'api',
      script: './src/api.js',
      instances: 2,
      exec_mode: 'cluster',
      env: { NODE_ENV: 'production', PORT: '3000' },
      max_memory_restart: '500M',
      watch: ['./src'],
      ignore_watch: ['node_modules'],
      cron_restart: '0 3 * * *',
      interpreter: 'node',
      max_restarts: 16,
      min_uptime: '1s',
      autorestart: true,
      merge_logs: true,
      kill_timeout: 5000,
    },
  ],
};

Migration tip: If you already have a PM2 ecosystem file, you can usually point Warden at it unchanged:

# Before
pm2 start ecosystem.config.js

# After
warden start ecosystem.config.js

Observability

PM2

  • Terminal: pm2 monit, pm2 list with inline CPU/memory
  • Cloud: PM2 Plus — web dashboard, alerts, multi-server (paid subscription)
  • Prometheus: Requires community modules or custom integration
  • REST API: Limited; full API tied to PM2 Plus

Warden

  • Terminal: warden monit, warden list, warden describe
  • HTTP API: Built-in on port 9615 — /processes, /processes/:id/metrics?range=1h, /summary, /health
  • Prometheus: Native /metrics endpoint with warden_process_* gauges
  • Time-series: SQLite database with 5-second sampling and 24-hour retention

Example Prometheus scrape config for Warden:

scrape_configs:
  - job_name: warden
    static_configs:
      - targets: ['127.0.0.1:9615']

Architecture

PM2                              Warden
────                             ──────
CLI (pm2)                        CLI (warden)
  │                                │  JSON-RPC over Unix socket
  ▼                                ▼
God Daemon                       God Daemon
  ├─ Process fork/cluster          ├─ ProcessSupervisor (fork)
  ├─ File watch                    ├─ ClusterManager (cluster)
  ├─ Log management                ├─ WatchManager (chokidar)
  ├─ Cron restart                  ├─ CronScheduler (croner)
  ├─ Memory monitor                ├─ MemoryMonitor (pidusage)
  └─ PM2 Plus (optional cloud)     ├─ MetricsSampler → SQLite
                                   ├─ LogRotator
                                   └─ HTTP API (Fastify + prom-client)

Both use a long-running god daemon that outlives the CLI. The CLI connects, sends commands, and exits — managed processes keep running.

When to choose PM2

  • You need PM2 Plus cloud monitoring, alerts, or multi-server fleet management
  • You rely on pm2 deploy for Git-based deployment workflows
  • You use the PM2 module ecosystem (pm2-logrotate, custom modules)
  • You need pm2 attach, pm2 trigger, or JSON output (pm2 jlist) for automation
  • You want an official Docker image with PM2 pre-installed
  • You need Windows service integration out of the box

When to choose Warden

  • You want a fully self-hosted solution with no cloud dependency or subscription
  • You need native Prometheus metrics and a built-in HTTP API without extra modules
  • You want local time-series metrics (SQLite) for debugging and short-term analysis
  • You prefer an MIT-licensed, TypeScript codebase you can fork and extend
  • You're running a single server or small fleet and terminal + Prometheus/Grafana is enough
  • You're migrating from PM2 and your workflow is: start → logs → monit → save → startup

Quick migration guide (PM2 → Warden)

# 1. Save your current PM2 process list (for reference)
pm2 save
pm2 jlist > pm2-backup.json

# 2. Stop PM2 (optional — they can coexist on different sockets)
pm2 kill

# 3. Install Warden
npm install -g @roshan-gamage/warden

# 4. Start your apps with the same ecosystem file
warden start ecosystem.config.js

# 5. Persist and enable boot startup
warden save
warden startup    # follow printed instructions for systemd / launchd

# 6. Verify
warden list
warden ping
curl http://127.0.0.1:9615/health

If you start processes individually instead of via an ecosystem file, recreate them with equivalent warden start flags (see CLI mapping above), then warden save.

Summary

Dimension Winner
Core process management (fork, cluster, restart, logs) Tie — feature parity for everyday use
Ecosystem config compatibility Tie — same file format
Built-in observability (API, Prometheus, metrics DB) Warden
Cloud monitoring & fleet management PM2 (PM2 Plus)
Module / plugin ecosystem PM2
Deployment automation PM2 (pm2 deploy)
Licensing & self-hosting Warden (MIT, no cloud lock-in)
Maturity & community PM2 — larger user base, longer track record

Warden covers the PM2 workflow most teams actually use — start, supervise, log, monitor, persist, and boot — while adding first-class telemetry. PM2 remains the better choice when you need cloud dashboards, deployment tooling, or the module ecosystem.
