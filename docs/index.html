Warden Process Manager

A self-hosted, PM2-equivalent process manager for Node 18+. Supervise any process — Node.js, Python, Ruby, binaries — with cluster mode, auto-restart, real-time logs, built-in Prometheus metrics, and a SQLite telemetry store.

Get started GitHub HTTP API

Fork & Cluster mode

Manage any interpreter in fork mode, or Node.js apps in multi-instance cluster mode with port sharing.

Auto-restart & backoff

Crash detection with exponential backoff, max restarts, and a min-uptime stability gate.

Zero-downtime reload

Rolling reload for cluster apps. Graceful restart for fork-mode processes.

Built-in Prometheus

Native /metrics endpoint with per-process CPU, memory, restarts, and uptime gauges.

SQLite time-series

5-second sampling with a 24-hour rolling window — no external services required.

HTTP REST API

Query process state, time-series metrics, and aggregate summaries over HTTP.

Ecosystem config

Declare multiple apps in a single ecosystem.config.js — PM2-compatible format.

Persistence

warden save / warden resurrect with systemd and launchd startup hooks.

Installation

From npm (recommended)

bash
npm install -g @roshan-gamage/warden

From source

bash
git clone https://github.com/RoshanGamage01/warden.git
cd warden
npm install
npm run build
npm link        # optional: make `warden` available globally

The compiled binary is at ./dist/bin/warden.js after build.

Linux prerequisites

Note

Warden depends on better-sqlite3, which requires native compilation. Prebuilt binaries are included for Node 20–24. If you see not found: make, install build tools:

bash
sudo apt-get update && sudo apt-get install -y build-essential python3

Quick Start

bash
# Start a Node.js script
warden start ./server.js --name api

# Start a Python worker
warden start ./worker.py --interpreter python3 --name worker

# Run 4 cluster instances (Node.js, port-sharing)
warden start ./app.js --instances 4 --name app

# Start all apps from an ecosystem file
warden start ecosystem.config.js

# View process list
warden list

# Stream logs from all processes
warden logs

# Live terminal dashboard
warden monit

# Persist and enable on boot
warden save
warden startup

CLI — warden start

Starts a process or all apps declared in an ecosystem config file.

syntax
warden start <script | ecosystem.config.js> [options]

Script examples

bash
# Node.js (default interpreter)
warden start app.js --name api --instances 2

# Python
warden start predict.py --interpreter python3 --name ml

# Binary
warden start /usr/local/bin/my-service --interpreter none --name svc

# Pass script arguments
warden start worker.js --name worker -- --queue=email --concurrency=5

# With environment variables
warden start app.js -e NODE_ENV=production -e PORT=3000

# With file watching
warden start app.js --watch --name dev-api

# With memory limit
warden start app.js --max-memory-restart 512M

# With cron restart
warden start app.js --cron "0 3 * * *" --name nightly
Tip

If you run warden start with an existing --name, the process config is updated and it is restarted in-place rather than creating a duplicate.

CLI — stop / restart / reload

CommandDescription
warden stop <id|name>Send SIGTERM, wait for graceful exit, then SIGKILL after kill_timeout. Status becomes stopped.
warden restart <id|name>Hard stop then immediate restart. Crash counter is reset.
warden reload <id|name>Cluster: rolling reload — new workers come up before old ones exit. Fork: graceful restart (same as restart).
bash
warden stop api           # by name
warden stop 0             # by warden_id
warden restart api
warden reload app         # zero-downtime for cluster apps
Warning

warden reload achieves zero downtime only for cluster-mode processes. Fork-mode processes will experience a brief restart window.

CLI — logs / flush

CommandDescription
warden logsStream stdout+stderr from all processes. Press Ctrl+C to stop.
warden logs <id|name>Stream logs for a specific process only.
warden logs -n <N> [id]Show last N historical lines first, then stream live output. Default tail: 15 lines.
warden flushTruncate all log files.
warden flush <id|name>Truncate log files for one process.
bash
warden logs              # all processes, stream live
warden logs api          # by name
warden logs 0            # by id
warden logs -n 100 api   # last 100 lines then stream
warden flush             # clear all logs
warden flush api         # clear logs for 'api' only

Log lines are prefixed with [name|id][out/err] so you can distinguish processes and stream types.

Logs are written to ~/.warden/logs/<name>-<id>/out.log and err.log. Files are rotated when they exceed 10 MB (configurable via max_log_size), with up to 5 backup files kept.

CLI — delete / scale / reset

CommandDescription
warden delete <id|name>Stop and remove the process from the registry. Log files and metrics are also deleted. Alias: del.
warden scale <id|name> <n>Scale a cluster-mode app to n workers at runtime. Adds or removes workers without downtime.
warden reset <id|name>Reset the restart and unstable-restart counters to zero.
bash
warden delete old-service
warden scale app 8        # scale to 8 cluster workers
warden scale app 2        # scale back down
warden reset api          # clear restart counters
Note

warden scale only works on cluster-mode processes (exec_mode: 'cluster'). Fork-mode processes are single-instance by design.

CLI — save / resurrect

CommandDescription
warden saveSerialize the current process list to ~/.warden/dump.json.
warden resurrectRead dump.json and restart any process that was online or launching at save time.
bash
warden save        # call this after your setup is stable
warden resurrect   # used by the startup service on boot

The dump file is plain JSON — human-readable and version-controllable if needed.

CLI — startup / unstartup

Generates and installs a system-level service so Warden (and your processes) auto-start on boot.

CommandDescription
warden startupAuto-detect platform and install service. Prints the required sudo commands.
warden startup systemdGenerate a systemd unit file (/etc/systemd/system/warden.service).
warden startup launchdGenerate a launchd plist (macOS: ~/Library/LaunchAgents/com.warden.daemon.plist).
warden unstartupRemove the installed startup service.
bash
# Run once after your processes are configured and saved
warden save
warden startup
# → follow the printed instructions (usually one sudo command)

The startup service runs warden resurrect on boot, which brings back all processes that were saved as online.

CLI — kill / ping

CommandDescription
warden killSend SIGTERM to the daemon, gracefully stopping all managed processes and shutting down the HTTP API.
warden pingConnect to the daemon and print: PID, version, started_at, socket path, and API port.
bash
warden ping
# Warden daemon · pid 12345 · v1.0.2
# Socket  ~/.warden/daemon.sock
# API     http://127.0.0.1:9615
# Uptime  3h 41m

warden kill
# ✔ Daemon (pid 12345) sent SIGTERM

Daemon lifecycle

The daemon is a long-running background process (god process) that persists after the CLI exits. It is auto-spawned the first time any warden command is run. The CLI communicates with it over a Unix domain socket using JSON-RPC with 4-byte length-prefixed frames.

Start Options

All options can also be set in an ecosystem config file.

-n, --name <name>
default: script filename
Assign a human-readable name. Used in all commands instead of the numeric ID.
-i, --instances <n|max>
default: 1
Number of cluster workers. Use "max" to spawn one per logical CPU. Implies --exec-mode cluster.
--exec-mode <mode>
default: fork
fork (any process, single instance) or cluster (Node.js, multiple workers sharing a port).
--interpreter <binary>
default: auto-detected
Interpreter binary. Examples: python3, ruby, node. Use none for compiled binaries.
--node-args <args>
default: none
Extra arguments passed to the Node.js runtime itself (before the script). Example: "--max-old-space-size=2048".
--cwd <dir>
default: process.cwd()
Working directory for the spawned process.
-e, --env <KEY=VAL>
repeatable
Inject environment variables. Can be repeated: -e PORT=3000 -e NODE_ENV=production.
--watch
default: false
Watch the working directory for file changes and restart the process. Uses chokidar under the hood.
--max-memory-restart <size>
default: disabled
Auto-restart when RSS memory exceeds this threshold. Accepts 150M, 1G, or a plain number (bytes). Checked every 5 seconds.
--cron <expr>
default: disabled
Schedule a restart via a cron expression. Example: "0 3 * * *" (daily at 3am). Uses croner.
--max-restarts <n>
default: 16
Maximum number of crash restarts before the process is marked errored and stopped.
--min-uptime <time>
default: 1s
Minimum uptime needed to consider a restart "stable" and reset the crash counter. Accepts 1s, 500ms, or milliseconds.
--restart-delay <ms>
default: 0
Base delay in milliseconds between restarts. Combined with exponential backoff, capped at 15 seconds.
--no-auto-restart
default: autorestart=true
Disable crash-triggered auto-restart. The process is stopped after first exit.
--merge-logs
default: false
Write stdout and stderr to the same out.log file instead of separate files.
--kill-timeout <ms>
default: 1600
Time in milliseconds to wait for graceful shutdown (SIGTERM) before sending SIGKILL.

Ecosystem Config

Declare multiple applications in a single configuration file and start them all with one command.

Supported file names

Warden recognizes any of these as an ecosystem file:

  • ecosystem.config.js
  • ecosystem.config.json
  • warden.config.js
  • Any file matching *.config.js

Full example

ecosystem.config.js
module.exports = {
  apps: [
    // Node.js cluster app
    {
      name: 'api',
      script: './src/api.js',
      instances: 4,              // or 'max'
      exec_mode: 'cluster',
      env: {
        NODE_ENV: 'production',
        PORT: '3000',
      },
      max_memory_restart: '500M',
      kill_timeout: 5000,
    },

    // File-watched development server
    {
      name: 'dev-server',
      script: './src/server.js',
      watch: ['./src'],
      ignore_watch: ['node_modules', 'logs'],
      env: { NODE_ENV: 'development' },
    },

    // Scheduled job
    {
      name: 'cleanup',
      script: './jobs/cleanup.js',
      cron_restart: '0 2 * * *',   // 2am daily
      autorestart: false,           // run once per schedule
    },

    // Python ML worker
    {
      name: 'ml-model',
      script: './predict.py',
      interpreter: 'python3',
      autorestart: true,
      max_restarts: 5,
      min_uptime: '5s',
    },

    // Binary service
    {
      name: 'sidecar',
      script: '/usr/local/bin/sidecar',
      interpreter: 'none',
      args: ['--port', '8080'],
      merge_logs: true,
    },
  ],
};
bash
warden start ecosystem.config.js

HTTP API

The daemon exposes a REST API on http://127.0.0.1:9615 by default. Change the port with WARDEN_API_PORT.

Endpoints

GET /health Daemon liveness check

Returns { "status": "ok", "pid": 12345 }

GET /processes All processes with latest metrics

Returns an array of process objects including warden_id, name, status, pid, exec_mode, instances, restarts, uptime, cpu, memory, script, cwd, out_log_path, err_log_path, instances_list, created_at.

GET /processes/:id Single process + 120 recent metric points

:id can be the numeric warden_id or the process name. Returns the full process object plus a recent array of { ts, cpu, memory } points.

GET /processes/:id/metrics?range=1h Time-series data for a process

Query params: range — time window. Supported: 1h (default), 6h, 24h, 7d. Also accepts raw seconds/minutes: 30m, 3600s.

Returns { warden_id, name, points: [{ ts, cpu, memory }, …] }.

GET /summary Aggregate system-wide totals

Returns { total, online, stopped, errored, launching, total_cpu_percent, total_memory_bytes }.

GET /metrics Prometheus exposition format

Returns all Warden gauges plus standard Node.js process metrics (via prom-client) in Prometheus text format.

Example requests

bash
curl http://127.0.0.1:9615/health
curl http://127.0.0.1:9615/processes
curl http://127.0.0.1:9615/processes/api
curl "http://127.0.0.1:9615/processes/api/metrics?range=6h"
curl http://127.0.0.1:9615/summary

Prometheus / Grafana

Warden exposes metrics in Prometheus text format at GET /metrics. Point your scrape config at the daemon API port.

Prometheus scrape config

prometheus.yml
scrape_configs:
  - job_name: warden
    scrape_interval: 15s
    static_configs:
      - targets: ['127.0.0.1:9615']

Available metrics

warden_process_cpu_percent{warden_id, name}
warden_process_memory_bytes{warden_id, name}
warden_process_restarts_total{warden_id, name}
warden_process_uptime_seconds{warden_id, name}
warden_process_online{warden_id, name, status}

Plus all standard prom-client Node.js process metrics (process_cpu_seconds_total, process_resident_memory_bytes, etc.).

Grafana

Add a Prometheus data source pointing to your server, then query any of the metrics above to build dashboards. Useful panel types:

  • Time series: warden_process_cpu_percent, warden_process_memory_bytes
  • Stat: sum(warden_process_online) — online process count
  • Counter: increase(warden_process_restarts_total[1h]) — restarts in the past hour

Architecture

CLI (warden) │ JSON-RPC over Unix domain socket │ [4-byte BE uint32: body length][UTF-8 JSON payload] ▼ Daemon (God process) ├─ IPC Server — socket listener, RPC request router ├─ DaemonRouter — dispatches to all subsystems ├─ AppRegistry — registry of all managed apps + their state │ ├─ ProcessSupervisor — fork-mode: spawn, crash detect, backoff │ └─ ClusterManager — cluster/master.js → N workers ├─ WatchManager — chokidar fs.watch → restart on change ├─ CronScheduler — croner → scheduled restart ├─ MemoryMonitor — pidusage poll every 5s → restart if over limit ├─ MetricsSampler — pidusage every 5s → MetricsStore (SQLite) ├─ LogManager — per-process file writes, tail, watch, rotate └─ HTTP API (Fastify) — REST + Prometheus /metrics

Daemon bootstrap sequence

  1. CLI checks if ~/.warden/daemon.sock is connectable.
  2. If not found, CLI spawns the daemon detached: node dist/daemon/index.js.
  3. CLI polls the socket every 100 ms (up to 5 seconds) for readiness.
  4. Once ready, CLI connects and sends the JSON-RPC command.
  5. After receiving the response the CLI exits; the daemon continues running.

IPC framing

wire format
┌──────────────────────┬───────────────────────────────────┐
│ 4 bytes (BE uint32)  │  N bytes (UTF-8 JSON)             │
│  body byte length    │  RpcRequest | RpcResponse | Event │
└──────────────────────┴───────────────────────────────────┘

Handles TCP fragmentation and multiple messages arriving in the same chunk.

Process State Machine

[*] ──► launching ──► online ──► stopping ──► stopped │ │ │ │ └──► launching (crash + autorestart) │ └──► errored (exceeded max_restarts) └────────────────────────────────► stopped (stop called)
StatusMeaning
launchingProcess was just spawned; waiting for the spawn event from Node.js.
onlineProcess is running and PID is known. Stability timer is counting.
stoppingSIGTERM sent; waiting for graceful exit or kill_timeout.
stoppedProcess exited cleanly (or was stopped intentionally).
erroredCrashed more than max_restarts times. Warden stops trying.

Windows Support

Warden runs on Windows with one adaptation: the Unix domain socket is replaced with a named pipe:

path
\\.\pipe\warden-daemon

All other functionality is identical. The pidusage and better-sqlite3 packages are both cross-platform.

Warning

If prebuilt binaries are not available for your Node version, native compilation is required. On Windows, install Build Tools for Visual Studio. The warden startup command does not yet generate a Windows service; use Task Scheduler or a third-party service wrapper manually.
